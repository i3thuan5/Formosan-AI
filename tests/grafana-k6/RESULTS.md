#### 分析

1. **`mt` 加 GPU 設定後爆發性加速（9.09×、−89%），是這次評測最大的變化。** 這證實了「幫 `mt` 的服務加上 GPU 設定」確實生效——先前主機雖然已經是 V100，但 `mt` 服務本身很可能還是吃 CPU 算力（類似第 2 次報告裡 `asr-kaldi`／Vosk 的狀況），調整後延遲從「秒級」直接降到「零點幾秒級」，變成四個模型裡最快的。
2. **其餘三個模型幾乎沒有變化**（asr −5%、tts −7%、asr-kaldi +2%），都在單輪線上測試常見的誤差範圍內，符合預期——這次改動只針對 `mt`，其他服務的部署沒有調整，彼此也沒有互相搶資源的跡象。
3. **排名重新洗牌，模型間的差距不減反增。** 上次（換到 V100 後）四模型的差距從 T4 時的 5.8 倍收斂到 3.9 倍；這次因為 `mt` 一枝獨秀衝到最快，差距反而重新拉開到 **12.2 倍**（`tts` / `mt`）。這不是退步，只是「最慢的沒動、最快的變更快」的自然結果——若目標是壓低平均體感延遲，這是好事；但若目標是讓各功能延遲更平均，現在 `asr-kaldi` 與 `tts` 變成相對最需要優化的兩個。
4. **`mt` 先前的離群值（11.29s）這次沒有再出現**，但只跑了一輪，建議之後多跑幾次確認離群值是否真的隨設定調整而消失，還是單純這次沒遇到。

#### 注意事項（比較時的限制）

- 這次跟上次只相隔約 2 小時、主機沒換，是乾淨的「只改 `mt` 設定」比較，干擾因素比第 1→2 次的比較少。
- 一樣只有 1 個 VU、依序執行，量的是「無人搶資源」情況下的延遲，不是併發吞吐量。
- `asr` 這次 p99（1.06s）比上次（0.90s）略高、`max`（1.24s）也偏高，但中位數與 p90 都持平或更低，判斷是單筆偶發延遲，不是系統性變化。

#### 分析

1. **`tts` 是最大受益者，換 GPU 幾乎是這次升級的主要理由。** F5-TTS 是 diffusion 架構、`nfe_step=32`，運算量遠高於其他三個模型，V100 比 T4 強得多的 FP16/Tensor Core 算力直接反映在延遲上——平均延遲砍半以上（6.65s → 2.88s），使用者感受最明顯的等待大幅縮短。
2. **`asr`（Whisper，ct2 float16）也有清楚的加速**（1.54×），符合預期：它跟 `tts` 一樣是 GPU 密集的深度學習模型。
3. **`asr-kaldi`（Vosk）與 `mt`（NLLB-600M）進步有限（約 10%）。**
   - `asr-kaldi` 本來就跑在 CPU 上（見第 1 次報告觀察 1），換 GPU 對它幫助很小，這次的結果也驗證了這個推論。
   - `mt` 用的 NLLB-600M 模型不大，運算量本來就不是瓶頸，換 GPU 帶來的邊際效益自然較小；且這次 `mt` 出現了一筆 11.29s 的離群值把平均值拉高，若排除離群值影響可能加速幅度會更接近 asr-kaldi 或略高。（後續：第 3 次報告顯示 `mt` 真正的瓶頸其實是沒有設定使用 GPU，補上設定後才是決定性的加速。）
4. **換機後排名沒有改變，但整體體感延遲明顯下降。** 四個模型的排序（asr 最快、tts 最慢）在兩次測試中一致，代表相對瓶頸沒有轉移；但因為原本最慢的 `tts` 進步幅度最大，模型之間的落差被拉近了，使用者跨功能切換時的延遲感受會比以前均勻。
5. **代價與效益需要放在一起看。** V100 的算力／記憶體頻寬都高於 T4，但雲端計費通常也更貴；這份報告只回答「換機後延遲變化多少」，是否划算需另外對照 TWCC 的計費差異。

#### 注意事項（比較時的限制）

- 兩次測試都只有 1 個 VU、依序執行，量的是「無人搶資源」情況下的延遲，不是併發吞吐量；V100 在高併發（多 VU／多 GPU 記憶體佔用）下的相對優勢可能更大，但本測試無法回答這個問題。
- 兩次測試間隔約 23 天，除主機／GPU 型號外無法完全排除模型版本或設定的變動；本比較假設除硬體外其餘條件不變。
- `mt` 的離群值（11.29s）建議之後多跑幾輪確認是否為偶發，不要單憑這一次的最大值／p99 下結論。

### 觀察

1. **`asr`（Whisper）比 `asr-kaldi`（Vosk）快 2.4 倍。** 這與直覺不符——Kaldi/Vosk 是 CPU 的
   輕量模型，Whisper-large-v2 是大模型。合理的解釋是線上的 Whisper 有 GPU（ct2 float16）
   可用，Vosk 則是在 CPU 上跑，再加上它是一塊一塊（4000 bytes）掃描音檔。
2. **`tts` 是效能瓶頸。** F5-TTS 是 diffusion 架構，`nfe_step=32` 要跑 32 步，
   還要過 vocoder，所以 10 秒以內的短句就要 5～9 秒。使用者感受最明顯的等待就在這裡。
3. **尾端（tail）很穩定。** 四個模型的 p99 都沒有偏離太多，只有 `asr`（max 4.09s）與
   `asr-kaldi`（max 6.06s）各有 1 筆特別高的，看起來是偶發的（cold start 或當下有
   其他人在使用），不是系統性的問題。
4. **100 次全部沒有失敗**（`http_req_failed` 0%、`checks` 100%），
   每次的辨識／翻譯／合成結果都通過內容檢查。
